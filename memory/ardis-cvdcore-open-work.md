The redesign is done and building clean. The main window is the operator mimic diagram; trends, PID Viewer and Process Parameters are separate windows. Deliberately unfinished, in order of how close each is to working:

**Cooling sensors — un-parked 17.08.2026 off a photographed wiring diagram, widened to seven circuits 24.08.2026.** The real wiring is NOT one module per quantity: the circuits use combined flow+temperature sensors (FlowTemp1..7, 4 wires each), so a circuit's flow and temperature sit on adjacent channels of the same module. U8/J7 = Flow1,Temp1,Flow2,Temp2,Flow3,Temp3,Flow4,Temp4; U9/J8 = Flow5,Temp5,Flow6,Temp6,Flow7,Temp7,WaterPressure,CDA — the second module carries THREE combined sensors, not two, so it is full and the pressures sit on AI7/AI8, not AI5/AI6. Sensors go to AIn-U with return on AIn-G; AIn-I unused. GVL arrays are `awCoolMod1Value/Status` + `awCoolMod2Value/Status`, both 16/8 words, both slaves configured identically. The seventh circuit is **Tuner**, listed in the HMI directly under MW Power, so HMI order and wiring order differ and `PRG_Cooling.C_FLOW_CH` is now an explicit table `[0,2,4,6,12,8,10]` rather than arithmetic. That grew the register block to 206..239 (`awHolding[0..239]`): 7 temps 206..219, 7 flows 220..233, water 234/235, CDA 236/237, masks 238/239, and the pressure validity bits moved from flow-mask bits 6/7 to 8/9 because the seventh circuit took bit 6. `PLC210CoolingClient` offsets moved with it — PLC and HMI must be flashed/rebuilt together. Modules are at 192.168.1.13 (U8) and 192.168.1.11 (U9); Unit-ID 1, and the INTEGER registers 16#0FE0/16#0FE8 are read, 8 words each -- see [[mv210-102-modbus-map]]. Verified live 18.08.2026 on module 1 only: flows all at 1.00 V (zero, pump off), temps 24.5..25.8 degC; U9 AI5/AI6 have never been read live. **The two pressure transmitters are NOT the same and their channels are not in the order the diagram suggests** — confirmed live 24.08.2026: AI7 = water (0..6 bar, volts/1.666, reads 1.7..1.8 on this loop), AI8 = CDA (0..10 bar, i.e. 1 bar per volt, reads about 7 on shop air). Getting either wrong shows 1.7 air / 4.2 water. This is also why ArdisCVDMaster published CDA raw in volts with its `/= 1.666` commented out (ICPDAC_IO.cs:517) while scaling water on the next line — on a 1 bar/V transmitter raw volts already read as bar, so the old display was accidentally right. Every channel is 0..10 V because the -102 offers no 0..5 V option. Waveguide/Rod is not on the diagram at all — no sensor, row hidden, and it is a different thing from Tuner. **Assumed, not confirmed:** FlowTemp1..7 = Stage, Chamber, MW Head, MW Power, Internal, External, Tuner (which is also what picks the 1..5 V scaling family), and Tuner's 4 l/min-per-volt flow span. No flow threshold or interlock exists — that is still policy nobody has decided.

**Process Parameters — one group of five works.** Chamber PID (P/I/D/H/L) edits `ChamberPid`; the gains were removed from PID Viewer so this is the only place that owns them. Four groups are `Enabled = false` with "— not implemented yet" appended to their captions: Alarm/Abort Parameters, Alarm/Abort Temperature Parameters, Inputs, Gas Correction Factor.

**The user challenged that.** They are right that Gas Correction Factor and most of Alarm/Abort have their signals already: all six gas flows, chamber pressure, Hi-Vac and reflected MW power are read, and gas setpoints are written. What is actually missing is policy, not measurement — three questions were about to be asked when the user said "пока забьём":
- GCF semantics: multiply the setpoint on write, scale the reading on display, or both.
- What Abort does: only kill the microwave ("Abort MW Power" per the combo text), also close the gas valves, or signal only for now.
- Where alarms surface: Status plate and its window, plus optionally a popup or a log file (there is no log file yet).
Two rows in that group can never work as drawn: Plasma drop has no sensor at all, and Plenum's PID channel is written `Enabled = false`.
Note from the reference: each gas alarm was gated on that gas's valve **and** GPV8 being open, and the percentage is measured against the commanded setpoint. Without that gate an alarm fires on every ramp after Set.

**Still fully inert:** Automatic Mode and everything recipe-related, the File menu, the press-and-hold pressure ramp on Chamber Pressure Set, and the microwave slope ramp. `TempLoopDelayTimer` and `ChamberPressureSlopeTimer` exist from the design and are unused.

**Session of 25.08.2026 — microwave, lid, tower.** Everything below is edited but NOT built and NOT flashed; the user was still bug-hunting. The HMI now disbelieves the microwave echo signals (see [[plc210-register-contract]]): PREHEAT greys out and the countdown/progress bar stay put unless the generator answers, Incident/Reflected and the six gas flows show "---" instead of a frozen number, and a generator that is merely switched off is no longer an Error on the Status plate — it gets a grey "Not connected" label in the Microwave section instead. **Reversed in part on 26.08.2026:** the user asked for that Status-window row to be Warning rather than OK, so an idle generator now turns the plate and the signal tower yellow between runs (the Microwave section label stays grey). A chamber lid switch on an FDI terminal was added end to end: `awHolding[139]`, `GVL_PlcIO.st`, `SystemStatus.AddChamberLid` first in the list, Error when open. **The PLC must be reflashed for that or register 139 reads 0 and the lid shows permanently OPEN.** The signal tower now lights all three lamps steadily on HMI link loss instead of blinking yellow.

**The .st files are a hand-carried mirror, and they have already drifted.** On 25.08.2026 `PLC_PRG.st` and `GVL_PlcIO.st` on disk were overwritten by a comment-stripped export from CODESYS, which arrived with a duplicated traffic-light block, `xHmiLinkLost` never assigned at all, and no clearing of `wTrafficLightMask` — three reasons the tower could not light, all fixed. That export also showed the user's CODESYS project does NOT contain the TON-based HMI watchdog the repo had (`fbHmiStale`, `HMI_STALE_TIME`, `udiHmiWritesSeen`, the bench lever `xForceHmiLinkLost`); it uses `HMI_STALE_CYCLES : UDINT := 15`, i.e. 3 s only while MainTask stays at 200 ms. The TON version is still in `git show HEAD:codesys/PLC_PRG.st`. Before diagnosing anything in ST, read the file — do not assume the repo and the PLC agree.

**Open question, physically dangerous, asked and not yet answered:** the gas channel order differs between the two sides. `PRG_GasFlow.st` has `axSlaveError[2] := MFC_O2` with `aFullScaleSccm[2] = 50.0` and `[3] := MFC_N2` with 1000.0; `PLC210GasFlowClient.GasNames/FullScaleSccm` have N2 at index 2 (1000) and O2 at index 3 (50). The retired driver agrees with the PLC (slave 3 = O2, slave 4 = N2). If the PLC is right, the N2 box shows O2's flow and a Set on N2 writes the O2 channel — whose spinner allows 1000 sccm against a 50 sccm scale, i.e. any N2 setpoint over 50 saturates the oxygen regulator wide open. Nothing was changed pending the answer: which РРГ-20 is on RS485 address 3 and which on 4.

**Other questions left hanging from that session:** should PREHEAT also be blocked on generator faults the way MICROWAVE is; should an open lid interlock anything (microwave, gas) or only be reported; should the trends draw a gap instead of plotting frozen values; and should `PRG_Microwave` re-issue the preheat command when the generator comes back.
